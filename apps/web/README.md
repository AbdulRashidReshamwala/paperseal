# Paper Seal web app

The board-hosted app, on port 5171. `/board`, `/setter`, `/centre` and `/keyholder` are lazy route areas, so each role downloads only its own code. Each area is one guided page: the exam's state picks the one screen to show, so there are no tabs, and old links such as `/board/outbox` or `/centre/unlock` land on the screen the state calls for. Set `VITE_TEE_URL`, `VITE_RPC_URL`, `VITE_REGISTRY_ADDRESS` and `VITE_EXAM_ID` at build time.

`VITE_RELEASES_REPO` is optional. It is the `owner/name` GitHub repository the board reads sealed machine versions from, `AbdulRashidReshamwala/paperseal` when unset, so a fork can set its own. Any other shape is an error.

`VITE_VERIFIER_URL` is optional. The public verifier is a separate app, hosted on its own, so the board's last screen links to this address. It must be `http` or `https`. If it is unset or invalid, that screen says the link is not set, and nothing else changes.

The release flow in `src/release` is shared by `/centre` and `/keyholder`, so it must stay free of paper and `K_priv` handling. That code lives in `src/areas/centre`. ESLint rules in `apps/eslint.config.mjs` and `src/boundaries.test.ts` enforce this.

## Board: create and publish an exam

The board follows six steps: create the exam, preview and submit (the sealed machine version is a row in the review, newest checked one already chosen), bring people in, wait, record the sealed paper, then watch the status. `/board` is the home list (not a step), and its "Create an exam" button opens the create page at `/board/new` on an empty form. An exam is reached at `/board/exam/<id>` (or `/board?exam=<id>`), which shows the step it has reached, and a draft at `/board/draft/<id>`. `/board/blueprint` and `/board/schedule` redirect to `/board/new`, `/board/publish` opens its review, and `/board/onboarding`, `/board/list` and `/board/outbox` open the exam this browser last published. The first two steps hold one form over five pages in the board route area: name, date and time (the typed name becomes an ENS label, shown under the field), topics, centres, neutral parties, and preview and submit. Names chosen for centres and neutral parties stay in the draft and move to `paperseal.parties.<id>` when the exam is published, so step 3 opens with them ticked. Nothing is saved until something is typed; then the form is a draft in the list `paperseal.board.drafts` in localStorage (id, last edited time, form and step), autosaved and kept until the exam is published, so it survives moving between steps and a reload on its `/board/draft/<id>` route. A draft saved by an older version under `paperseal.board.draft` moves into the list on first read. The home list shows drafts (Continue, Delete with one confirm) and published exams (Open) together, newest first. Each published exam is read on its own, three at a time and every 5 seconds at most, and its row shows a plain status from `examState` (`decideStep`, `sealStateAt`): "Unavailable" when the read fails, or one word for its stage (Unpublished, Inviting, Collecting, Building, Ready, Posted, Finished or Failed). On first load the whole list, drafts included, is a skeleton with one placeholder per row (read to screen readers as "Checking…") until every exam has a read, a failed one included, or 8 seconds pass; a row still unread then shows a skeleton bar for its status. The rest of the page shows at once, and later polls never bring the skeleton back. With no exams or no registry there is no skeleton. Only the current exam is asked what Paper Seal says, since the machine serves one exam. "Open an exam by its ID" opens an exam this browser does not know. Published exams are kept in `paperseal.board.exams` (id, the name typed and when it was published, since ExamRegistry stores only the name's hash); older exams are found from `paperseal.examId` and the `paperseal.invites.<id>` keys, without a name. Publishing sends `createExam` from the connected browser wallet (`window.ethereum`, through viem's custom transport) on Sepolia. The app holds no private key. Before sending it checks that the wallet is on chain 11155111 and that its account equals `registry.board()`, dry-runs the call so reverts are explained in words, and after mining reads `getExam` and `getCriteria` back and compares them with what was entered. The published exam ID is kept in this browser's localStorage, only when the read-back matches, so the flow carries on with it without a rebuild. `VITE_EXAM_ID` is the fallback. Every area (Register, key holder, centre, setter, release and the board) reads the one current exam from `src/shared/currentExam.ts`, and a key holder and a centre keep separate stored credentials.

The exam name must be one normalised ENS label, such as `jee-main-2026` ("Exam Names" in `spec/api.md`). The create step checks it with `examNameProblem` from `@paperseal/protocol` and refuses anything else, such as `Maths 2026`, `JEE-Main-2026` (it suggests `jee-main-2026`) or `jee.main`, without changing what was typed, because another spelling hashes to another exam ID. The status step has an optional folded "Give this exam an ENS name" section listing the records to set on `<exam name>.<your primary name>`, filled from this app's own settings: the ETH address is `VITE_REGISTRY_ADDRESS`, and the `ens.records` text keys hold `VITE_TEE_URL`, `VITE_STORAGE_URL` and `VITE_TEE_STORAGE_BUCKET`. A missing value shows as not set. The exam name is known only in the session that published it, and is otherwise shown as `<exam name>`. With `VITE_VERIFIER_URL` set, it also shows the verifier's `#/name/<exam name>.<your-name>.eth` link. Nothing here reads ENS. The steps are in `docs/ens-setup.md`.

Tests: `pnpm test` runs everything except the anvil test. `pnpm test:integration` starts `anvil --chain-id 11155111`, deploys `contracts/out/ExamRegistry.sol/ExamRegistry.json` (run `forge build` in `contracts/` first) and publishes through `packages/chain`. It uses anvil's public dev key, only in `src/integration/anvil.integration.ts`.

To try it by hand against anvil, deploy with `BOARD_ADDRESS=<anvil account 0> forge script script/Deploy.s.sol --broadcast --rpc-url http://127.0.0.1:8545` from `contracts/`, add anvil's account to a wallet on a chain with ID 11155111 and RPC `http://127.0.0.1:8545`, and run the app with `VITE_RPC_URL=http://127.0.0.1:8545 VITE_REGISTRY_ADDRESS=<deployed address> pnpm dev`. For Sepolia, use the board's deployed `ExamRegistry` address and a Sepolia RPC URL.

## Key holder and centre

`VITE_DIRECTORY_NAME` is the parent ENS name of the directory, `paperseal-demo.eth` by default. `VITE_STORAGE_URL` is the public storage base (files are read from `<base>/<examId>/<name>`), and `VITE_TEE_STORAGE_BUCKET` is the only environment variable the attestation check allows in the token. The release flow checks the TEE with `checkToken` and seals the share to `encryptionPublicKey` only when `trusted` is true. The share is HPKE-encrypted to its holder alone, so there is no time seal on it: the file is checked against the manifest, and the manifest against the Build. Centres download and check `paper.bin`, `key-pub.tlock` and the manifest ahead of time, and at unlock fetch K_pub from drand, open `key-priv/<derivedPublicKey>.bin`, and show the paper only if its salted hash equals the Build's. `PaperSheet` shows a multiple choice question's options as an A, B, C list under it, in the paper's order and styled for print. Both roles take their passkey from `shared/RegisterByName.tsx` and their derived key from the on-chain approved list.

## Board: onboarding and outbox

Step 4 is choosing who takes part. Key holders and centres are ticked from the directory, the `paperseal.directory` record on `VITE_DIRECTORY_NAME` (`paperseal-demo.eth` by default), with a role each, and the choice is kept under `paperseal.parties.<examId>`. A small field adds a name that isn't listed. The board shares one public exam link, `#/exam?exam=<examId>`. A registration joins the list only if its owner is the chosen name, its `inviteTag` is 32 zero bytes, and its passkey hash equals the name's `paperseal.passkey` record. A name with no record, or a record for another key, stays off the list, and a name that can't be read offers "Try again". See "Party Names" in `spec/api.md`.

Setters get one invite each, with a private note. The app makes a random 32-byte secret and a link to copy, and everything sits in the link's URL fragment, `#/join?exam=..&role=setter&secret=..`, so no server sees it. The invites are kept in this browser's localStorage under `paperseal.invites.<examId>`, and that is the only copy, so "Save a backup" matters. The step reads the registrations the TEE verified from `GET /v1/registrations` and recomputes each `inviteTag` from its stored secrets. If two keys match one invite, both are left off until the board makes a new link. Registrations that fit nothing show only as a count.

## Setter

`/setter` is one page. A setter registers from their invite link, waits for the list, and then the app confirms the TEE by itself (attestation and the on-chain list hash). The confirmation lasts 5 minutes. Before each question is sealed, the app reads a fresh attestation and requires the same keys. A question is sealed with `examId || passkeyPublicKey` as the HPKE aad. If a send is ambiguous, the sealed question is kept in memory, so a retry sends the same ciphertext instead of a second copy. The question text is dropped once its receipt is verified. The composer offers Written (the default) or Multiple choice. A multiple choice question starts with two option fields and takes up to `limits.questionOptionsMax`; the form refuses a blank or repeated option inline, trims options before sealing, and keeps their order. It has no field for the correct answer, because the paper becomes public. `protocol`'s `parseQuestion` and `encodeQuestion` enforce the same rules, and a written question still encodes to the same bytes as before.

## Registration

A setter's invite link opens `/join`. `src/shared/Join.tsx` reads the fragment once with `decodeInviteFragment` (strict: exactly the expected keys, each once, a lowercase 32-byte secret, role `setter`), holds the invite in memory (`src/shared/invite.ts`), sets the current exam, and replaces the address with `/setter`, so the secret is not left in the address bar or the browser history. Reloading forgets it, and opening the link again restores it. `Register` shows nothing to type, and one key touch.

A key holder or centre enrols once at `/enrol` (`src/shared/Enrol.tsx`) and sends the key card to whoever runs the directory. They then register per exam at `/exam` (`src/shared/ExamPage.tsx` and `RegisterByName.tsx`), which reads the name's records, so it works in any browser on this domain. It takes two touches. The credential is stored for both holder pages, because the board decides the role. A key already on the posted list, or already held by the TEE under this name, needs no touch: a new browser only learns it. The key holder and centre pages offer no registration once the exam has ended.

## Demo keys

`pnpm demo:keys` starts this app in the `demo-keys` Vite mode, with a bar that switches who you are acting as and a planted key per person, for showing a whole exam in one tab. `src/shared/demoKeys.ts` is the only door to `src/demo`, and `src/demoKeys.test.ts` checks a production build holds no trace of it.
