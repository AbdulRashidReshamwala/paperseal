# Paper Seal web app

The board-hosted app, on port 5171. `/board`, `/setter`, `/centre` and `/keyholder` are lazy route areas, so each role downloads only its own code. Each area is one guided page: the exam's state picks the one screen to show, so there are no tabs, and old links such as `/board/outbox` or `/centre/unlock` land on the screen the state calls for. Set `VITE_TEE_URL`, `VITE_RPC_URL`, `VITE_REGISTRY_ADDRESS` and `VITE_EXAM_ID` at build time.

`VITE_RELEASES_REPO` is optional. It is the `owner/name` GitHub repository the board reads sealed machine versions from, `AbdulRashidReshamwala/paperseal` when unset, so a fork can set its own. Any other shape is an error.

`VITE_VERIFIER_URL` is optional. The public verifier is a separate app, hosted on its own, so the board's last screen links to this address. It must be `http` or `https`. If it is unset or invalid, that screen says the link is not set, and nothing else changes.

The release flow in `src/release` is shared by `/centre` and `/keyholder`, so it must stay free of paper and `K_priv` handling. That code lives in `src/areas/centre`. ESLint rules in `apps/eslint.config.mjs` and `src/boundaries.test.ts` enforce this.

## Board: create and publish an exam

The board follows seven steps: create the exam, choose the sealed machine version, review and publish, bring people in, wait, record the sealed paper, then watch the status. `/board` shows the step the exam has reached. `/board/blueprint` and `/board/schedule` start a new exam, and `/board/publish` opens its review. The first three steps hold one form in the board route area, so it survives moving between them. Publishing sends `createExam` from the connected browser wallet (`window.ethereum`, through viem's custom transport) on Sepolia. The app holds no private key. Before sending it checks that the wallet is on chain 11155111 and that its account equals `registry.board()`, dry-runs the call so reverts are explained in words, and after mining reads `getExam` and `getCriteria` back and compares them with what was entered. The published exam ID is kept in this browser's localStorage, only when the read-back matches, so the flow carries on with it without a rebuild. `VITE_EXAM_ID` is the fallback. Every area (Register, key holder, centre, setter, release and the board) reads the one current exam from `src/shared/currentExam.ts`, and a key holder and a centre keep separate stored credentials.

The exam name must be one normalised ENS label, such as `jee-main-2026` ("Exam Names" in `spec/api.md`). The create step checks it with `examNameProblem` from `@paperseal/protocol` and refuses anything else, such as `Maths 2026`, `JEE-Main-2026` (it suggests `jee-main-2026`) or `jee.main`, without changing what was typed, because another spelling hashes to another exam ID. The status step has an optional "Give this exam an ENS name" card listing the records to set on `<exam name>.<your primary name>`, filled from this app's own settings: the ETH address is `VITE_REGISTRY_ADDRESS`, and the `ens.records` text keys hold `VITE_TEE_URL`, `VITE_STORAGE_URL` and `VITE_TEE_STORAGE_BUCKET`. A missing value shows as not set. The exam name is known only in the session that published it, and is otherwise shown as `<exam name>`. With `VITE_VERIFIER_URL` set, it also shows the verifier's `#/name/<exam name>.<your-name>.eth` link. Nothing here reads ENS. The steps are in `docs/ens-setup.md`.

Tests: `pnpm test` runs everything except the anvil test. `pnpm test:integration` starts `anvil --chain-id 11155111`, deploys `contracts/out/ExamRegistry.sol/ExamRegistry.json` (run `forge build` in `contracts/` first) and publishes through `packages/chain`. It uses anvil's public dev key, only in `src/integration/anvil.integration.ts`.

To try it by hand against anvil, deploy with `BOARD_ADDRESS=<anvil account 0> forge script script/Deploy.s.sol --broadcast --rpc-url http://127.0.0.1:8545` from `contracts/`, add anvil's account to a wallet on a chain with ID 11155111 and RPC `http://127.0.0.1:8545`, and run the app with `VITE_RPC_URL=http://127.0.0.1:8545 VITE_REGISTRY_ADDRESS=<deployed address> pnpm dev`. For Sepolia, use the board's deployed `ExamRegistry` address and a Sepolia RPC URL.

## Key holder and centre

`VITE_STORAGE_URL` is the public storage base (files are read from `<base>/<examId>/<name>`), and `VITE_TEE_STORAGE_BUCKET` is the only environment variable the attestation check allows in the token. The release flow checks the TEE with `checkToken` and seals the share to `encryptionPublicKey` only when `trusted` is true. The share is HPKE-encrypted to its holder alone, so there is no time seal on it: the file is checked against the manifest, and the manifest against the Build. Centres download and check `paper.bin`, `key-pub.tlock` and the manifest ahead of time, and at unlock fetch K_pub from drand, open `key-priv/<derivedPublicKey>.bin`, and show the paper only if its salted hash equals the Build's. `PaperSheet` shows a multiple choice question's options as an A, B, C list under it, in the paper's order and styled for print. Both roles take their passkey from `shared/Register.tsx` and their derived key from the on-chain approved list.

## Board: onboarding and outbox

Step 4 is invites. The board adds one invite per person (a role, plus the name for the approved list, or a private note for a setter), and the app makes a random 32-byte secret and a link to copy. Everything an invite holds sits in the link's URL fragment, `#/join?exam=..&role=..&owner=..&secret=..`, so no server sees it. The invites are kept in this browser's localStorage under `paperseal.invites.<examId>`, and that is the only copy, so the board has to be opened in the same browser to see who has registered. The step then reads the registrations the TEE verified from `GET /v1/registrations` and recomputes each `inviteTag` (`HMAC-SHA-256(inviteSecret, passkeyPublicKey)`) from its stored secrets. A registration joins the list only if its tag and owner match an invite. A registration with no matching invite is shown as not invited and left off. If two keys match one invite, both are left off and the invite shows "Reissue invite", which makes a new secret and link. Key holders and setters get their role from their invite, and only a centre's place (with or without a key) is a choice. The app composes the list with `encodeApprovedList` after `checkApprovedList`, and posts it with `postApprovedList` from the wallet. The list slot is write-once, so posting stays blocked until the TEE passes attestation for the current exam against the chain and is at the `onboard` stage. The screen shows the exam being written, in a folded exam record, and the check runs again right before the wallet is asked. Setters register with no name, from an invite link that has none. Their `owner` is the `setterOwner` hash of their own passkey public key, and `checkApprovedList` rejects any other value. Step 6 appears once the outbox holds the Build, and verifies its TEE signature against an attested instance key before `postBuild`.

## Setter

`/setter` is one page. A setter registers from their invite link, waits for the list, and then the app confirms the TEE by itself (attestation and the on-chain list hash). The confirmation lasts 5 minutes. Before each question is sealed, the app reads a fresh attestation and requires the same keys. A question is sealed with `examId || passkeyPublicKey` as the HPKE aad. If a send is ambiguous, the sealed question is kept in memory, so a retry sends the same ciphertext instead of a second copy. The question text is dropped once its receipt is verified. The composer offers Written (the default) or Multiple choice. A multiple choice question starts with two option fields and takes up to `limits.questionOptionsMax`; the form refuses a blank or repeated option inline, trims options before sealing, and keeps their order. It has no field for the correct answer, because the paper becomes public. `protocol`'s `parseQuestion` and `encodeQuestion` enforce the same rules, and a written question still encodes to the same bytes as before.

## Registration links

An invite link opens `/join`. `src/shared/Join.tsx` reads the fragment once with `decodeInviteFragment` (strict: exactly the expected keys, each once, a lowercase 32-byte secret, a name the TEE accepts), holds the invite in memory (`src/shared/invite.ts`), sets the current exam, and replaces the address with the role's page (`/keyholder`, `/centre` or `/setter`), so the secret is not left in the address bar or the browser history. The invite lasts as long as the page stays open. Reloading forgets it, and opening the link again restores it. Nothing is written to storage on this side except the registered credential, which also keeps its `inviteTag`, so a different link for the same role (a reissue) asks for a new registration and an old key stops counting.

`Register` shows the role and name from the link, with nothing to type, and one key touch. With no valid link it explains that registration needs the link, and shows no form. The key holder and centre pages offer no registration once the exam has ended (the end round has passed, or the sealed machine says `released` or `failed`), and there is no "register a different key" button on any page, because a second key on one invite would leave both off the list until the board reissues it.
